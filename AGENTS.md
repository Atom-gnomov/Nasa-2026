# Інструкції для агентів

Проєкт: NASA Space Apps Challenge 2026 — вебзастосунок для порівняння місць і дат посадки на Місяці
(Сонце й Земля над горизонтом, енергія, зв'язок, радіація, температура).

## Мова — ОБОВ'ЯЗКОВО
**Усі агенти пишуть українською мовою:**
- відповіді та повідомлення команді;
- уся документація (`docs/`, `README.md`, цей файл);
- описи комітів і pull request'ів;
- коментарі в коді.

Винятки: ідентифікатори в коді (змінні, функції, файли) — англійською; оригінальний текст завдання в `docs/CHALLENGE.md` лишається англійською; власні назви (NASA, LOLA, DSN тощо) не перекладаємо.

## Гілка `coordination` — спільні документи (читати першою)
- **Уся тека `docs/`** (діздоки, задачі, дошка, пропозиції) **живе й змінюється в гілці `coordination`**, а не в `main` і не в гілках задач. Копія `docs/` у `main` оновлюється із запізненням.
- **Перед будь-якою роботою** — `git fetch origin` і `python tools/agents/status.py`, документи читати з `origin/coordination`.
- Зміни в `coordination` — прямим push без PR, лише після `git pull --rebase`; force push заборонено. Код туди не комітимо.
- Код, тести, `contracts/`, `tools/`, `app/` — гілки задач і PR у `main`. Гілки задач `docs/` не змінюють.
- Права на документи й покрокові команди (зокрема `git worktree` для `coordination`) — `docs/BOARD.md` у гілці `coordination`.
- Синхронізацію `coordination` ↔ `main` робить Перун.

## Імена агентів і дошка
- Кожен агент має ім'я: **Перун** — власник і його агент Claude; пул для інших — **Велес, Ярило, Сварог, Стрибог, Чорнобог**.
- Ім'я задає власник у завданні; якщо не задано — візьміть перше вільне ім'я з [docs/BOARD.md](docs/BOARD.md) і запишіть себе туди.
- **Що зараз робите й що вже зробили — заявляйте в `docs/BOARD.md` у гілці `coordination`** (правила — там же). Редагуйте лише свій розділ.
- Назва гілки: `<ім'я латиницею>/<ID задачі>-<коротко>`, наприклад `veles/B3-timeline`, `perun/M4-lola-dem`.

## Перед кожною задачею — обов'язково
```bash
python tools/agents/status.py --check <ID>   # підтягує стан, показує чужі гілки й заявки
```
1. **Не дублювати:** якщо задача вже є в чужій гілці чи на дошці (`main` або гілки агентів) — беріть іншу.
2. **Свіжий `main`:** нова гілка — лише від щойно підтягнутого `origin/main`.
3. **Заявити одразу — у `coordination`:** свій розділ у `docs/BOARD.md` + статус 🔄 у `docs/TASKS.md`, одразу `git push origin coordination`. Лише потім — гілка задачі від свіжого `main`.

## З чого почати
1. [docs/CHALLENGE.md](docs/CHALLENGE.md) — оригінальний текст завдання (англійською).
2. [docs/VISION.md](docs/VISION.md) — вимоги команди. **Головний документ.** Дотримуйтеся його; якщо він розходиться із завданням, пріоритет має VISION. Обсяг першої версії — розділ «MVP».
3. [docs/MODULES.md](docs/MODULES.md) — вимоги до модулів, статуси, API. **Перед задачею знайдіть свій модуль.**
4. [docs/MATH.md](docs/MATH.md) — математика розрахунків (формули, перевірені контрольні числа). **Обов'язково для задач М5–М8.**
5. [docs/CONTRACTS.md](docs/CONTRACTS.md) — контракти API, даних і фронтенду. **Змінюєте API чи формат даних — спершу контракт** (`contracts/openapi.yaml`, `contracts/schemas/`).
6. [docs/RESOURCES.md](docs/RESOURCES.md) — джерела даних, бібліотеки та запропонований стек візуалізації.
7. [docs/TASKS.md](docs/TASKS.md) — **дрібні задачі, хвилі й доріжки для паралельної роботи 2–6 агентів.** Беріть задачу звідси й ставте статус.
8. [docs/PROPOSALS.md](docs/PROPOSALS.md) — пропозиції та покращення (додавати за шаблоном).

## Запуск і перевірки
```bash
python -m venv .venv && . .venv/bin/activate
pip install -r requirements-dev.txt   # включно з ефемеридами DE440 (~114 МБ)
flask --app app run --debug   # http://127.0.0.1:5000
python -m pytest              # тести — обов'язково перед push
```

## Правила
- Головний користувач — **планувальник місій**: точні метрики й швидке порівняння сценаріїв важливіші за красу.
- Тривалості показуємо в **земних годинах**.
- Спочатку робимо MVP, другу чергу — лише після нього.
- Нові рішення команди записуємо в журнал рішень у `docs/VISION.md`, а неясності — у розділ «Відкриті питання».

## Робота з git: як уникати конфліктів

### Злиття в `main` — лише за рішенням власника
- **Зливати в `main` може тільки Перун — власник репозиторію (`Atom-gnomov`) або його агент за прямою вказівкою.** Ніхто інший `main` не змінює.
- **Усі, включно з власником і його агентом, пишуть у своїх гілках**, а в `main` потрапляють лише через PR.
- PR від інших учасників потребують схвалення власника (файл `.github/CODEOWNERS`).
- PR власника та його агента схвалення інших учасників **не потребують**: їх зливає власник.
- Агенти не зливають PR самі, без прямої вказівки власника в розмові.

### Гілки
- **Ніколи не пушити напряму в `main`.** Усі зміни — лише через pull request.
- **Одна задача — одна гілка.** Назва: `<ім'я>/<ID>-<коротко>`, наприклад `veles/B3-timeline` (імена — `docs/BOARD.md`). Для робіт поза TASKS.md — `<ім'я>/<коротко>`.
- Гілка живе недовго: невеликий PR, швидке злиття, гілку видаляємо.

### Постійно стежити за `main`
`main` змінюється, коли Перун зливає чужі PR. Щоб не накопичувати конфлікти:
- **підтягувати `main`** на початку роботи, перед кожним push, після кожного злиття в `main` і не рідше ніж раз на 1–2 години роботи:
  ```bash
  git fetch origin
  git rebase origin/main        # своя гілка, якою ніхто інший не користується; далі git push --force-with-lease
  # або: git merge origin/main  # якщо гілку вже хтось переглядає
  ```
- `python tools/agents/status.py` показує, на скільки комітів гілка відстає від `main`;
- після злиття свого PR — нова гілка лише від свіжого `origin/main`, старі коміти не використовувати;
- перед push — запустити перевірки (лінтер, тести).

### Дивитися на сусідні гілки
- Перед взяттям задачі й перед PR — `python tools/agents/status.py`: він показує активні гілки агентів, їхні задачі й заявки на дошках у цих гілках.
- Якщо ваша задача торкається файлу, який змінює чужа активна гілка, — перегляньте її зміни (`git diff origin/main...origin/<гілка> -- <файл>`) і домовтеся через дошку або Перуна, хто змінює першим.

### Заборонено
- `git push --force` у `main` і в чужі гілки. У власній гілці — лише `git push --force-with-lease`.
- Переписувати історію комітів інших людей.
- Масове переформатування або перейменування файлів «заодно» з іншою задачею — це окремий PR.

### Розподіл зон
- Одна задача змінює **лише файли своєї зони**. Якщо треба змінити чужу зону — окремий невеликий PR або домовленість у задачі.
- Зони = модулі з [docs/MODULES.md](docs/MODULES.md) (М1–М15). Коротко:
  - `docs/` — документація;
  - `app/core/<модуль>.py` + `tests/test_core_*.py` — математичне ядро (чисті функції, без Flask; формули — `docs/MATH.md`);
  - `app/services/<модуль>.py` + `tests/` — сервіси поверх ядра (метрики, DSN, каталог місць);
  - `app/routes/` — сторінки й API;
  - `app/templates/`, `app/static/css/` — верстка;
  - `app/static/js/<модуль>.js` — фронтенд-модулі (один файл — один модуль);
  - `tools/` — скрипти передрозрахунків.
- Спільні файли (`requirements*.txt`, `app/__init__.py`, `base.html`, `state.js`, `README.md`, `AGENTS.md`) змінювати мінімально й точково.
- Змінили інтерфейс модуля (функцію, поле API) — оновіть його опис у `docs/MODULES.md` у тому ж PR.
- Змінили поле API або формат даних — спершу `contracts/` і `docs/CONTRACTS.md`; контрактні тести (`tests/test_contracts.py`) мають пройти.
- Нові зовнішні дані підключаються лише через адаптер за протоколами `app/core/sources.py` (див. `docs/CONTRACTS.md`, розділ 4).

### Документи
- `README.md` та `AGENTS.md` змінюємо лише точковими правками. Не переписуємо їх повністю, не видаляємо чужі рядки без причини.
- Журнал рішень у `docs/VISION.md` — **лише дописуємо нові рядки в кінець**, старі не змінюємо.
- Хочете суттєво переписати документ — спершу питання в PR або в «Відкриті питання».

### Коміти та PR
- Коміт — одна логічна зміна, опис українською: що і навіщо.
- PR маленький (бажано до ~300 рядків змін), з описом: що зроблено, як перевірити.
- Якщо PR довго висить — регулярно підтягувати `main`, щоб конфлікти не накопичувались.

### Якщо стався конфлікт
1. Не викидати чужі зміни наосліп: подивитися, хто і навіщо змінив (`git log -p <файл>`).
2. Зберегти обидві зміни, якщо вони сумісні; якщо ні — уточнити в команди.
3. Після розв'язання — запустити перевірки ще раз.
